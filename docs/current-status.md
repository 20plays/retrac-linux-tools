# Current Status

Last updated from the active investigation on 2026-08-30.

## What works now

Retrac 3.0.9 launches under Wine Staging 11.16 with WebView2 functioning. OAuth custom-protocol handling can be registered with a Linux desktop entry, Alea installs successfully, the Alea Windows service starts, and its named pipe `\\.\pipe\AleaAntiCheat` is available.

The major breakthrough was getting AleaClient through its startup checks. After adding missing Windows-compatible session semantics and `SystemBootEnvironmentInformation`, AleaService logs show:

```text
Started Alea client suspended
Started game suspended
Exchanging process handles
Resuming Alea client
Waiting for Alea client to signal ready
Alea client signaled ready
Resuming game
Launch succeeded
Request completed successfully
```

At that point the service-side launch path is no longer the blocker.

## Remaining blocker

The protected `FortniteClient-Win64-Shipping.exe` wrapper still deliberately opens a fatal-error MessageBox.

A focused Wine relay trace and an external packet capture show the following sequence:

```text
TCP connect to alea-service-prod.retr.ac:80
GET /ws HTTP/1.1
server -> HTTP/1.1 101 Switching Protocols

client -> 38 bytes
server -> 50 bytes

client -> 34 bytes
server -> 36 bytes

client -> 46 bytes
server -> TCP ACK only

client -> 62 bytes
server -> TCP ACK only

~25 seconds with no application response
wrapper select() returns 0 (timeout)
wrapper enters fatal/error handling
wrapper suspends the companion process
wrapper displays fatal MessageBox
wrapper later closes TCP connection
```

The packet capture is important: the server ACKs the final messages, so they reached the remote peer. The remote peer does **not** close first. The wrapper's timeout is real, rather than a Wine `select()` bug hiding readable data.

## Strongest current hypothesis

The remaining divergence is likely **before or inside the client-state data sent in the final protocol messages**, not in basic networking.

Possible explanations still worth testing:

- A standard Windows API returns subtly different system state under Wine.
- A Windows-visible token/session/security property still differs.
- Some ordinary hardware/platform property generated by Wine differs from native Windows in a way the backend rejects.
- The backend intentionally declines to continue based on client state that is validly different on Wine.

The correct next move is a **native Windows reference run**, comparing packet direction/length/timing only, then building small standalone compatibility probes for any standard Windows APIs that differ.
